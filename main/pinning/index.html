    Pin your dependencies¶

    Aval reuses a result when the fingerprint of the declared inputs matches. The fingerprint hashes the text of your files. If a file says postgres:16, Aval hashes the words postgres:16, not the image behind them. When someone pushes a new image under that tag, the text stays the same, the fingerprint stays the same, and without a check Aval would reuse a result that was produced with a different image.

    A reference like that is mutable: its content can change while its name stays the same. Aval looks for mutable references in the files in the contract scope it recognizes (see each ecosystem below) and in runner.command, and refuses to reuse a result that depends on one.

    What Aval does with a finding¶

    Cacheability What happens
    hermetic, controlled-environment The lookup is a miss and the reason lists every reference. aval run runs the test; aval run --push and aval push do not publish the result. aval verify exits 4.
    external-dependencies The findings are printed as information. The class is not reusable by default anyway.
    non-deterministic Unchanged: never reusable.

    aval run prints one line per finding:

    mutable: compose.yaml:3 (container) postgres:16: a tag can be repushed: pin the image by digest (name:tag@sha256:...)

    The line names the file and line, the ecosystem, the reference as written, and what to pin. aval run --fingerprint-only prints the same lines on stderr, so stdout stays the digest.

    Detection is static and offline: Aval reads files, it never fetches, resolves or runs anything. It reads at most 1 MiB per file; a larger file it should check, or one it cannot read, is itself a finding. Lockfiles (pnpm-lock.yaml, go.sum, Cargo.lock, ...) are hashed but not scanned.

    Fix it by ecosystem¶

    Container images¶

    Pin every image by digest. Keep the tag for readers; the digest decides.

    # compose.yaml, Kubernetes manifests, rendered Helm charts
image: redis:7.4-alpine@sha256:c5d34a98396a4775e223c74e929162c35c5a2182901ba26b50ade939941ce14b

    FROM golang:1.25@sha256:<digest> AS build
FROM build AS test          # a stage name is fine
COPY --from=nginx:1.27@sha256:<digest> /etc/nginx /etc/nginx
ADD --checksum=sha256:<sum> https://example.com/tool.tgz /tool.tgz

    A # syntax= parser directive names the BuildKit frontend image: pin it too (# syntax=docker/dockerfile:1@sha256:<digest>).

    Aval reads a Dockerfile in two passes and reports what either finds:

    • The line pass reads each line as an instruction. It joins a continued line with a space and reads a RUN heredoc body as a script.
    • The BuildKit pass splits the file the way BuildKit does. It runs on files named Dockerfile, Dockerfile.*, *.dockerfile or any name that starts with Dockerfile and has no dot (Dockerfile-dev, Dockerfile_windows), and the same with Containerfile. A comment line stands alone, even when it ends in \. A continued line joins the next one with nothing between (FROM db:1\ then 6 is db:16). A leading # escape= sets the escape character, for continuations and for the heredoc words. RUN, COPY and ADD heredoc bodies are kept apart.

    Both passes check COPY --from= and RUN --mount=...,from= like a FROM: a stage name or index is fine, an image needs a digest. An instruction behind ONBUILD is checked like the same instruction without it. The line pass can misread a heredoc or a continuation; that costs a needless miss, never a false hit.

    The BuildKit pass also reports:

    • a file BuildKit refuses: an invalid # escape=, a repeated directive, an unterminated heredoc;
    • a heredoc name with a quote, \ or $ in it (<<#\\x, <<E$X), or an empty one (<<""), which Aval does not decode;
    • a FROM image with a variable that is not a global ARG with a value. In FROM, BuildKit expands only the ARGs declared before the first FROM. A stage ARG, an ENV or an ARG without a value is reported by its line (FROM alpine:$V): give the global ARG a default, or write the image.

    A kustomization.yaml that retargets an image in images: (or the legacy imageTags:) with newName or newTag needs a digest: too.

    images:
  - name: postgres
    newTag: "16"
    digest: sha256:<digest>

    Aval reads the kustomization as kustomize does (field names in any case, merge keys resolved), but it does not build the overlay. It reports these entries by name and index (resources[2], patches[0]):

    • a resources, components or bases entry that is remote (a URL, git::, github.com/...) or not in the scope: vendor it into the scope;
    • a patches, patchesStrategicMerge, patchesJson6902 or replacements entry that sets an image (an image: key, a JSON6902 path or from ending in /image, a fieldPath ending in .image);
    • a patches, patchesStrategicMerge or patchesJson6902 entry given by a path not in the scope;
    • a transformers or generators entry with an image transformer, or a path not in the scope;
    • a helmCharts entry, unless the chart is local (no repo), its Chart.yaml is in the scope under helmGlobals.chartHome (default charts; an absolute one, or one that leaves the kustomization directory, is not local), and it has no valuesInline that sets an image. Its templates are checked like any other file, if the scope includes them.

    A tagSuffix is always reported: kustomize drops the digest when it adds the suffix. A kustomization that is not valid YAML, or that kustomize could not decode, is reported by its path.

    Find the digest with docker buildx imagetools inspect <image:tag> or crane digest <image:tag>. Images in docker run, podman run and docker compose commands, and kubectl run/create --image, follow the same rule. A compose file the command uses must be in scope.source, so its images get checked too; a compose file can be YAML or JSON (compose.json). An image that comes from a variable Aval cannot resolve (${DB_IMAGE}) or from a Helm template ({{ .Values.image }}) is reported: write the digest into a file in the scope, or render the chart into the scope. A YAML alias (image: *img), a block scalar (image: >-) or a tag (image: !!str ...) is reported too: write the reference inline.

    YAML is read in two passes too. The line pass matches image: in every line, also inside a block scalar a template renders (extraContainers: |). The YAML parser matches every key that decodes to image ("ima\x67e":, ? image, !!str image:, !!binary aW1hZ2U=:), wherever its value is. A key with another tag (!custom image:) is reported. A Compose build.dockerfile_inline is checked as a Dockerfile, and build.additional_contexts values with docker-image:// as images.

    When the parser rejects a file (a Helm template), Aval reports what it cannot decode: a tagged key, a quoted key with an escape YAML cannot decode, an escaped image key whose value is elsewhere, and a quoted key that continues on the next line. In *.tpl files, files under templates/ and files the parser rejects, a key a template writes (ima{{ "ge" }}:, {{ $k }}:) is reported by its text. The exception is the key variable of a range loop alone ({{ $key | quote }}:) directly under labels: or annotations:: it names a label, not a field.

    JSON is read the same way, but only in Compose files (compose.json), files under templates/ and files a kustomization in scope lists in resources, so package.json and other data files stay quiet.

    Go¶

    Commit go.sum and add it to scope.dependencies. It pins every module by hash. In commands, use release versions:

    go install golang.org/x/tools/cmd/stringer@v0.30.0   # not @latest or @main

    JavaScript: npm, yarn, pnpm, bun¶

    Commit the lockfile (package-lock.json, yarn.lock, pnpm-lock.yaml or bun.lock) and add it to scope.dependencies. Without one, every range (^1.2.0, latest, *) is reported. Install from the lockfile and pin what you run:

    npm ci
npx --yes prettier@3.3.3

    Python¶

    Pin every requirement with == and, better, with hashes. Generate the file instead of writing it by hand:

    uv pip compile --generate-hashes requirements.in -o requirements.txt
pip install --require-hashes -r requirements.txt

    If a requirements file uses hashes, every entry needs one. Poetry needs poetry.lock and Pipenv needs Pipfile.lock next to the manifest. A pyproject.toml with [project] dependencies needs uv.lock, pdm.lock or poetry.lock, next to it or at the workspace root. A git requirement needs a full commit id: pkg @ git+https://host/repo@<40-hex>. Any requirements*.txt path is checked, also requirements/dev.txt. A file named by pip install -r or -c must be in the scope, so its pins get checked; otherwise it is reported. The same holds for a -r/-c include line inside a requirements file (resolved next to that file).

    Rust¶

    Commit Cargo.lock (at the workspace root) and add it to scope.dependencies. In commands, use cargo install tool --version 1.2.3.

    Java: Maven and Gradle¶

    Use release versions. 1.0-SNAPSHOT, LATEST, RELEASE, dynamic versions (1.+, latest.release) and ranges ([1.0,2.0)) are reported in pom.xml, build.gradle, build.gradle.kts and *.versions.toml.

    Ruby and PHP¶

    Commit Gemfile.lock (or gems.locked) and composer.lock, and add them to scope.dependencies. In commands, use gem install tool --version 1.2.3.

    OS packages¶

    apt-get install, apk add, dnf/yum/microdnf install and zypper install install whatever the mirror has today. Pin versions (curl=8.5.0-2, jq=1.7.1-r0, curl-7.76.1-26.el9, vim=9.0) or, better, install the packages into an image and pin that image by digest.

    Helm¶

    helm install and helm upgrade of a chart that is not in the scope need an exact --version 1.2.3. A chart directory in the scope (its Chart.yaml) is checked as files.

    Scripts from the network¶

    curl … | sh (also through tee or other pipe stages), bash -c "$(curl …)", python -c "$(curl …)", eval "$(curl …)" and source <(wget …) run whatever the server sends. A curl or wget of a releases/latest URL fetches whatever release is newest. Dockerfile RUN instructions, including BuildKit heredoc bodies (RUN <<EOF), get the same shell checks. Vendor the script into the scope, or download a fixed version and check its sha256 before running it.

    Aval finds scripts by name: *.sh, *.bash, *.zsh, *.mk, Makefile, and in-scope files without an extension whose first line is a sh, bash, zsh, ksh or dash shebang (./setup). A script with another extension is hashed but not scanned.

    Git¶

    A git clone follows a branch or tag that can move: check out a full commit id in the same command (git clone URL && git -C dir checkout <40-hex>), one checkout per clone. A git pull is reported for the same reason. A submodule with a branch = line in .gitmodules, or git submodule update --remote, follows a branch: rely on the commit recorded in the repository.

    Resolve a reference instead¶

    To follow a tag, a range or a branch on purpose, declare the reference in scope.resolve: Aval resolves it to its digest, checksum or commit every time it fingerprints and hashes that id, so a move changes the fingerprint. It never clears a finding: the reference still blocks reuse until you pin it in place or accept it below. scope.resolve binds the artifact you name, not its dependencies: use a lockfile for those. See Resolve references.

    Accept a reference on purpose¶

    Sometimes a mutable reference is acceptable, for example an image your team rebuilds and scans every night. Acknowledge it in the contract, with the reason:

    scope:
  source: ["**/*.go", "compose.yaml"]
  allowMutable:
    - ref: postgres:16          # exactly as Aval prints it
      reason: rebuilt and scanned nightly; the tag is ours
    - file: deploy/kustomization.yaml   # only the finding in this file
      ref: resources[0]
      reason: vendored upstream base, reviewed on update

    file is the path Aval prints before the line number, relative to the contract (runner.command for the command). With it, the entry accepts the finding in that file only. Without it, the entry accepts the ref only when one file reports it: generic refs such as resources[0], patches[0] or a templated key repeat across files, so a ref that two files report is not accepted, and the finding asks for file. With scope.contracts, each contract's entries apply to its own findings, with file relative to that contract.

    ref must match the reference text Aval prints (for a missing lockfile, the manifest path, such as go.mod). Aval drops quotes from references it finds in shell commands, so "curl" -fsSL URL | bash prints as curl -fsSL URL | bash. The acknowledgement is part of the contract, so adding or removing one changes the fingerprint, and reviewers see it in the diff. aval run still prints the finding, marked (allowed: <reason>). A file Aval cannot read (larger than 1 MiB, or unreadable) is reported in the scan ecosystem and cannot be accepted: shrink or split it. A finding Aval reports because it cannot tell (a templated or tagged key, a kustomize entry such as resources[2], a heredoc name, a FROM line) is in the container ecosystem: acknowledge it by the ref Aval prints.

    Limits¶

    The scanner is a best-effort safety net, not a guarantee. The guarantee is the declared scope and the pins you write in place: a digest, a lockfile, a commit id. The detectors read text; they do not run your build, render your chart or apply your overlays, and a reference they do not recognize is not reported. Keep the scope honest, pin in place, and use aval run --shadow to catch false hits. Known limits:

    • Shell commands are split without a full shell parser: a quoted ; or > also splits, and a token misread as a package is reported as unpinned (a needless miss). An option Aval does not know to take a value (tool --opt value install x) hides the subcommand.
    • A download from an unversioned URL other than releases/latest (curl -o tool URL, curl URL | tar x) is not detected.
    • Helm: values that split an image into repository and tag, and YAML a template prints ({{ include ... }}, {{ toYaml ... }}), are not read. In a template the parser rejects, a key written as a block scalar or an alias is not decoded.
    • Kustomize: the overlay is not built. A JSON6902 patch file in the scope named by path: that sets an image is not read.
    • JSON outside Compose files, templates/ and kustomize resources is not read.
    • Dockerfile variables: outside FROM, the last value of a name wins, with no stage scoping. Values given at build time (--build-arg) are not seen: Aval checks the ARG default.
    • A source file whose name starts with dockerfile and has a dot (dockerfile_test.go) gets only the line pass.

    Declare what the scanner cannot see in scope.resolve (a url, an image), so its content is hashed.
