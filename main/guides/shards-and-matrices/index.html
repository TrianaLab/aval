    Shards and matrices¶

    Goal: a test suite split into shards across CI matrix jobs gets one result and one fingerprint per shard, each bound only to what that shard reads.

    flowchart LR
  m([matrix]) --> s1[shard 1: aval run -f aval.shard-1.yaml] --> r1([result 1]):::muted
  m --> s2[shard 2: aval run -f aval.shard-2.yaml] --> r2([result 2]):::muted
  c[change under packages/app] -. reruns .-> s2

    No new field: shards use -f, scope and environment.env. The example is examples/uv-monorepo, a uv workspace with two packages, which Aval's CI runs.

    Pattern A: one contract per shard¶

    Each shard has its own contract, metadata.name and scope. A file holds one contract and -f takes one path, so put the shard contracts side by side, each under its own name. Globs cannot contain ..: a contract lives in the directory that holds all its inputs, here the workspace root.

    # Shard 1 of 2: the core package's tests. It lives at the workspace root,
# beside aval.shard-2.yaml, because globs cannot leave the contract's
# directory and the uv workspace files are here. Run with
# `aval run -f aval.shard-1.yaml`.
apiVersion: aval.trianalab.io/v1
kind: Test
metadata:
  name: uv-monorepo-core
runner:
  command: ["uv", "run", "--locked", "--package", "core", "pytest", "packages/core", "--cov=core", "--cov-report=xml:coverage-shard-1.xml"]
scope:
  source: ["packages/core/**/*.py"]
  # uv checks the lock against every member's pyproject.toml.
  dependencies: [pyproject.toml, "packages/*/pyproject.toml", uv.lock, .python-version]
environment:
  toolchain: {python: "3.12", uv: "0.9.18"}
cacheability: hermetic
outputs: [coverage-shard-1.xml]

    Shard 2 tests app, which imports core, so core's code is in its scope:

    # Shard 2 of 2: the app package's tests. app imports core, so core's code is
# in scope here too; app's files are not in shard 1's scope.
apiVersion: aval.trianalab.io/v1
kind: Test
metadata:
  name: uv-monorepo-app
runner:
  command: ["uv", "run", "--locked", "--package", "app", "pytest", "packages/app", "--cov=app", "--cov-report=xml:coverage-shard-2.xml"]
scope:
  source: ["packages/app/**/*.py", "packages/core/src/**/*.py"]
  dependencies: [pyproject.toml, "packages/*/pyproject.toml", uv.lock, .python-version]
environment:
  toolchain: {python: "3.12", uv: "0.9.18"}
cacheability: hermetic
outputs: [coverage-shard-2.xml]

    A change under packages/app reruns shard 2 only. A change to core or to uv.lock reruns both. If shared code lives outside a directory you want for a shard, bind it with scope.contracts instead of widening the globs: Depend on another part of the repo.

    Pattern B: one contract, shard variables¶

    One contract for every shard, with the shard index and count as declared environment variables:

    # One contract for every shard of examples/uv-monorepo. Each matrix job sets
# SHARD_INDEX and SHARD_TOTAL, so each shard gets its own fingerprint over
# the whole suite's scope. Splitting by index needs a pytest plugin such as
# pytest-shard, which the example does not lock. pytest-shard counts
# SHARD_INDEX from 0: set it to `${{ strategy.job-index }}` and SHARD_TOTAL
# to `${{ strategy.job-total }}`.
apiVersion: aval.trianalab.io/v1
kind: Test
metadata:
  name: uv-monorepo-tests
runner:
  command: ["sh", "-c", "uv run --locked --all-packages pytest packages --shard-id=$SHARD_INDEX --num-shards=$SHARD_TOTAL"]
scope:
  source: ["packages/**/*.py"]
  dependencies: [pyproject.toml, "packages/*/pyproject.toml", uv.lock, .python-version]
environment:
  toolchain: {python: "3.12", uv: "0.9.18"}
  # Leave one out and every shard shares one fingerprint: a false hit.
  env: [SHARD_INDEX, SHARD_TOTAL]
cacheability: hermetic

    Each shard gets its own fingerprint, but over the whole suite's scope, so a change anywhere reruns every shard. Simpler to set up, less reuse.

    Declare both variables

    Leave SHARD_INDEX or SHARD_TOTAL out of environment.env and shards share a fingerprint: shard 2 reuses shard 1's result without running its own tests, a false hit.

    The matrix¶

    One job per shard. Shards that share a checkout write different --result files, and each declares its own coverage file under outputs, restored on reuse:

    # A two-shard matrix for this example as its own repository: copy it to
# .github/workflows/ and set REPO and POLICY. Each job runs one shard
# contract with its own --result; on main, reuses a verified result or runs
# the shard; for pull requests read POLICY and REPO from the default branch
# (docs/trust-model.md#take-the-policy-from-a-protected-branch). It uploads that shard's coverage, restored on reuse. Publishing
# needs the push step from Aval's "Use GitHub Actions" guide.
name: tests
on:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1, 2]
    env:
      REPO: ghcr.io/acme/uv-monorepo-aval
      POLICY: .github/aval/policy.yaml
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: astral-sh/setup-uv@68559e99cc807c1eb7e9238fd43a15bba460eec2 # v10.3.3
        with:
          version: "0.9.18"
          enable-cache: false
      - run: curl -fsSL https://aval.run/install.sh | bash -s -- --version v0.5.0
      - run: >-
          aval run -f aval.shard-${{ matrix.shard }}.yaml
          --result .aval/shard-${{ matrix.shard }}.json
          --registry "$REPO" --policy "$POLICY"
      - uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
        with:
          name: coverage-shard-${{ matrix.shard }}
          path: coverage-shard-${{ matrix.shard }}.xml

    The same job locally, for shard 2:

    aval run -f aval.shard-2.yaml --result .aval/shard-2.json --registry "$REPO" --policy "$POLICY"

    To publish, add the push step from Use GitHub Actions to each job. On pull requests, read the policy from a protected branch: Take the policy from a protected branch.

    Not built: several contracts in one call, templated contracts

    aval run takes one contract and reports one result. Your CI already runs the matrix jobs and aggregates their status. A contract with placeholders would make the scope computed instead of declared.
